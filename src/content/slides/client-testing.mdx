<section class="vstack vstack-tight">

<div class="eyebrow">Setup and test code get mixed together</div>

<h2>Use responses the server actually sends</h2>

<div class="body measure">Hand-written payloads can type-check and still describe a response Galaxy never sends. Repeated synthetic data also hides the test's story.</div>

<div class="callout measure">Record backend responses. Load typed fixtures. Keep only the scenario's overrides in the test.</div>

<div class="note"><a href="https://github.com/jmchilton/galaxy/tree/vitest_real_api_calls">Branch: vitest_real_api_calls ↗</a><br />Recorded API fixtures → history-summary factory → disk-usage tests. Separate from the story lane.</div>

<aside class="notes">[Sources] https://github.com/galaxyproject/galaxy/issues/24030; https://github.com/jmchilton/galaxy/tree/vitest_real_api_calls at 0277a85df395 (published October 20, based directly on readability); client/README.md “Recorded API Responses”. <div class="eyebrow">“But these aren't unit tests”</div>

<div class="statement">HOT TAKE: Unit tests are<br />a deeply human thing.</div>

<div class="lede">Part of their value is how they push us to think about the design. I don't see agents responding to that pressure the same way.</div>

<aside class="notes">[Sources] John's argument in /Users/jxc755/projects/repositories/galaxy-brain/vault/projects/just_jesting_around/SLIDES.md. This section presents my position on the tradeoff, not an empirical claim about every agent or every unit test.</aside>

</section>

<section class="vstack">

<div class="eyebrow">Decomposition</div>

<h2>Humans feel shame writing a bad test</h2>

<div class="body measure left">A ton of mocking. A test more complicated than the feature or fix. We know when we're writing a bad test — and the bad test is telling us the implementation sucks.</div>

<div class="callout measure">That pushes us to decompose and design better.</div>

<div class="note">Good unit tests require good decomposition. That feedback is part of their value.</div>

<aside class="notes">[Sources] SLIDES.md — the decomposition argument, adapted closely from John's wording.</aside>

</section>

<section class="vstack">

<div class="eyebrow">What I see with agents</div>

<div class="statement">They can write around the implementation<br />instead of rethinking it.</div>

<div class="body measure">What I keep seeing: a complicated implementation gets a complicated test. The agent makes it pass, and I'm left reviewing both.</div>

<div class="callout measure">I want the test to help us see when the design needs work.</div>

<aside class="notes">[Sources] SLIDES.md — John's observation about agent-generated tests. Softened from an absolute claim about agents to the pattern John observes in generated tests.</aside>

</section>

<section class="vstack">

<div class="eyebrow">The review loop</div>

<h2>Look at what these tests let us review</h2>

<div class="body measure">These Storybook tests communicate between the implementation, the agents, and the humans. That is the part I care about.</div>

<div class="callout measure">They're easier to review — and the review covers so much more when you can see the story in action.</div>

<aside class="notes">[Sources] SLIDES.md — John's review-time and communication argument. The earlier local benchmark shows a modest runtime cost; the review argument is about visible behavior, not runtime alone.</aside>
